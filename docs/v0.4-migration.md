# Migrating to Rosalind v0.4

v0.4 keeps receipt envelope schema 5 and preserves historical schemas 1–5, but it
intentionally makes file creation non-destructive and strengthens replay.

## Output behavior

Every file-producing command now defaults to create-new atomic output. If either the
destination or a reserved breach path already exists, the command exits 2 before
computation. Add `--force` only when replacing the final path is intentional.
Successful writes are flushed, synced, and atomically renamed. Governed breaches
are named `<output>.partial`; ordinary failures clean up temporary files.

## Analyzer contracts

Builders set `ContractRunSpec::analyzer_memory`, `enforcement`, and `output_policy`.
Unknown analyzer memory is allowed only for record-only observation. A fixed model
is a versioned maximum of additional retained bytes after runner startup. Existing
`ColumnAnalyzer` implementations remain source-compatible.

`--enforce` means cooperative governance. `--require-os-limit` additionally requires
an already-active, sufficiently tight Linux cgroup v2 `memory.max`; Rosalind does
not create or modify cgroups.

## Replay and trust

New receipts remain envelope schema 5 and use replay schema 3. Built-in recipes are
strictly validated and allowlisted. External analyzers require an explicit trusted
`--binary PATH`; a recorded executable path is never used. Inspect first with
`rosalind reproduce --dry-run --json`.

Verification output uses trust-report schema 2 while retaining the documented
schema-1 top-level fields. Receipt integrity, artifacts, resource assurance,
reproduction evidence, and signatures are separate facets. Missing evidence is not
reported as failure.

## Builder smoke path

```sh
rosalind demo
rosalind studio rosalind-demo/*.manifest.json rosalind-demo/*.repro.json
rosalind new analyzer example --output ./example
cargo build --manifest-path ./example/Cargo.toml
rosalind conformance analyzer --binary ./example/target/debug/example --json
```
